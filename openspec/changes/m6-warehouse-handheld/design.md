# Design

## Context

Today a zone is a `ZoneDefinition` (name plus `ZoneFilter`) copied onto each `StorageNodeBlockEntity` by `ZoneLabelItem.useOn`. `WarehouseZones` maps bay positions to those copies and feeds `PutAwayPlan` tiers; `StorageFill`, the controller screen, the terminal's Storage tab and `/servus_warehouse zones` group bays by the zone's lower cased name. Fluid Racks are stamped per section through `FluidRackBlock.stampSection`.

Foundation already has the pattern for team data the client must see: duct channels (`DuctChannelData` as overworld `SavedData` with a codec, pure `ChannelList` with name checks, `ChannelSync` broadcasting the list on join and on every change, `Teams.teamOf(player)` for the team id). Zones follow the same shape.

## Goals / Non-Goals

**Goals:**
- Zones as team data that bays reference by id, edited in one place.
- One handheld item with a mode framework that `m11-handheld-link` extends with LINK without rework.
- Feedback that feels like a scanner: sound, flash, scan line, action bar, HUD panel.

**Non-Goals:**
- No migration of label stamped zones (decided with the user; Zone Labels are removed outright).
- No custom first person rendering of the screen onto the item model; in the world the screen is a HUD panel, and the GUI draws the device.
- No change to what the Data Potato reports; its rack report only says shelf instead of section.

## Decisions

### Team zones mirror duct channels
`zone/ZoneList` (pure: id, team UUID, name, colour index 0 to 15, filter) with name rules 1 to 24 characters, unique per team ignoring case, ordering by name, text search and `resolve(id)` that turns an unknown id into "no zone". `zone/WarehouseZoneData` is overworld `SavedData` (`SavedDataType` with a codec, key `servus_warehouse_zones`), the only place that mutates the list, and `zone/ZoneSync` sends the full list to a joining player and to everyone after each change, held client side in `ClientZones`. The filter is stored as the existing `ZoneFilter` (ghost items and tags), so `PutAwayPlan` and the Fluid Rack fluid rule stay unchanged.

*Alternative:* keep stamped copies and add "restamp all bays of zone X". Rejected: copies drift, and the renaming problem is the reason for the change.

*Name length:* 24 like channels instead of the label's 32, so names fit the beam next to the code sticker.

### Bays hold a zone id
`StorageNodeBlockEntity` stores an `int` zone id (0 = none) instead of a `ZoneDefinition`, saved as `ZoneId`. The old `Zone` tag is not read, which drops label stamped zones on load. Display and filter are resolved through `WarehouseZoneData` on the server and `ClientZones` on the client. `WarehouseZones` keeps `pos -> id` and resolves the definition when it builds put-away tiers; grouping keys in `StorageFill`, `ProductionRows` and the command become the zone id as text, with the resolved name for display.

Editing a zone posts `WarehouseEvent.ZonesEdited` to every warehouse network of every loaded dimension (through Foundation's `NetworkManager` network sets), drained in the next tick like any other event, so tiers and storage rows refresh without polling. Client side, beams re-render from `ClientZones` because the rack renderer reads the name and colour each frame.

### Location codes are computed on the server and pushed to bays
`zone/LocationCode.of(dx, dy, dz)` is pure (`N`/`S` from `-dz`/`dz`, `E`/`W` from `dx`, zero as `N0`/`E0`, signed height, `+0` for zero). `WarehouseNetwork` knows `controllerPos`; whenever the controller joins or leaves, or a rack bay joins or leaves the network, the network sets the code of every shelf (an empty string without a controller) on each of its bays and the bays sync it in their update tag. Which bay of a shelf gives the code is decided in "Shelves, not bays" below. This is event driven and costs nothing per tick. The handheld reads the aimed bay's code from the client block entity, so the panel's top line needs no request.

*Alternative:* compute codes on the client from the controller position. Rejected: the client does not know which controller a bay belongs to.

### Handheld item and mode framework
`handheld/HandheldItem` with data components for mode (enum `HandheldMode`: ZONE, FIND, INFO; LINK is added by `m11-handheld-link`), active zone id, bound controller (dimension + pos), FIND target item and pinned bay. The item id is `servus_shuttles:handheld` and its name "Handheld HH-1", so later models (`HH-2`, `HH-3`) can be separate items sharing the class.

Mode switching: client `InputEvent.MouseScrollingEvent` (cancellable, NeoForge `net.neoforged.neoforge.client.event.InputEvent`) is cancelled while the player sneaks with the handheld in the main hand, and a `HandheldModePayload(step)` asks the server to change the component. The server owns the state.

### Scanning uses vanilla held-use repeat
Right click on a bay goes through `HandheldItem.useOn`. Vanilla repeats `startUseItem` every 4 ticks while the use key is held (`Minecraft.rightClickDelay = 4`, checked in 26.1.2 sources), so a sweep needs no custom input: each repeat lands on whatever bay the crosshair is on. The server tracks per player the last scanned bay and the sweep count (reset after 10 ticks without a scan), skips a repeat on the same bay silently, and sends a `HandheldScanPayload(positions, ok, sweepIndex)` that plays the beep at a pitch rising with `sweepIndex` and starts the flash. Since the 2026-10-30 revision every scan takes the whole shelf and the sweep tracks shelves, not bays (see "Shelves, not bays").

`HeavyRackBlock.useItemOn` and `FluidRackBlock` pass for the handheld (replacing the `ZoneLabelItem` check), so the rack GUI never opens and `useOn` runs. `controller/WarehouseControllerBlock` does the same for binding.

### HUD panel, scan line, flash and glow are client renderers
- Panel: a GUI layer registered with `RegisterGuiLayersEvent` (as `PlacementAssistHud` does), drawn while the handheld is in either hand, styled as the green LCD.
- INFO data: only a scan asks. Right clicking a bay in INFO runs through `useOn` like the other modes (beep and flash through `HandheldScanPayload`), stores the bay in the pinned bay component as "last scanned", and answers with `HandheldInfoPayload` (the scanned bay, the shelf's code, zone id, slots used and total, top items). Aiming sends nothing; the panel's top line still reads the aimed bay's code from the client block entity. Opening the GUI sends the readout of the last scanned bay again (`HandheldActions.resendInfo`), so the INFO screen survives a relog. A held repeat on the same shelf is skipped in every mode by the sweep tracker.
- Scan line, flash and FIND glow: `RenderLevelStageEvent.AfterTranslucentBlocks` (as `AnchorRangeRenderer` does). The flash is a fading box (`RenderTypes.debugQuads()`) and the glow an outline of crossed bands along the twelve edges drawn with `RenderTypes.textBackgroundSeeThrough()` (no depth test in 26.1.2) for the glow time; both cover a whole shelf, with the geometry in "Shelves, not bays". The scan line is a thin red quad from the hand offset to the hit point while use is held.
- FIND list and bay counts: opening the GUI sends `HandheldMenuStatePayload` with the loaded bays per zone id and the bound warehouse's stock (one stack per item with its count, largest first, from the warehouse index); it is sent again after every create, edit and delete. No separate stock request. Picking an item sends `HandheldFindPayload(item)`, and the server answers with `HandheldFindResultPayload` (item, total, one position per loaded shelf holding it with the shelf's code, glow ticks).
- The server side of the handheld (`handheld/HandheldActions`) takes any `Player`, not only a `ServerPlayer`, and sends payloads only to a `ServerPlayer`, so GameTests drive it with mock players.

### GUI drawn as the device (revised after the first play check, 2026-10-30)
The first build showed a plain container window on a Zones tab, which did not read as the handheld or as FIND. `client/HandheldScreen` now draws the device from `textures/gui/handheld.png` (generated like the other GUI textures): dark steel body, yellow rubber bumper with a darker rim, red scan window, the brand line "HH-1" and a green LED. The CRT is drawn in code over the screen area: fill `#0f1f12`, text `#8dff9a`, labels `#3f8a4a`, a tiled scanline texture (`textures/gui/handheld_scanlines.png`, every third row dark at about 18 % alpha), a vignette texture darkening the edges, and a faint glow whose alpha drifts a few percent over a few seconds (no hard flicker). Text uses the vanilla font in those colours.

Item icons on the CRT: the GUI renders items through the 26.1 render state, so there is no per item colour multiplier. Each icon is drawn normally and then covered by a square of `#0f1f12` at about 55 % alpha plus `#8dff9a` at about 25 %, which reads as a green phosphor icon; the hovered or selected item skips the overlay and shows in its own colours.

The screen opens on the view of the handheld's mode (ZONE list, FIND list, INFO readout); the old Zones and Find tab buttons go. Three softkeys under the screen (ZONE, FIND, INFO, the current one lit) send `HandheldModePayload(step, Optional<HandheldMode> target)`, and switch the view at once; the server side is `HandheldActions.applyMode`, which switches the handheld of the open GUI, else the one in the main hand. The menu holds no player inventory any more. On the CRT, New, Edit, Delete, Save, Cancel and Add are text buttons drawn on the screen (inverted while hovered), and the search and name lines are borderless green edit boxes. The textures come from `tools/handheld-textures/gen.py`: `handheld.png` (device and softkey sprites), `handheld_scanlines.png` and `handheld_vignette.png`.

### Zone filter through the item picker
The zone form drops its nine ghost slots and the tag text line. The filter shows as a list of entries (items and `#` tags, up to nine of each) with an "Add" button that opens Foundation's `ItemPicker` with tag search on; picking adds the entry, clicking an entry removes it. The picker keeps its normal look over the CRT. The edit payloads carry the same `ZoneFilter` as before, so the server side is unchanged.

### Tag search in Foundation's ItemPicker
`ItemPicker` gains an opt-in tag search. When on and the search starts with `#`, the entries are built from the client's item tags (`BuiltInRegistries.ITEM` named tags; verify the 26.1.2 accessor, `Registry#getTags`, in the sources jar during apply) as entries whose id is `#ns:path`, icon the first item, label the id and the item count. Tab completes the search line to the top hit's id; the tooltip of a tag entry lists up to six items. Ordering lives in the pure `foundation/picker/TagSearch` (path prefix first, then id contains, each by id), covered by `TagSearchTest`. Only the zone form turns it on in this change; the duct filter can later.

### Beam stripe and code sticker
This was the first build, one label per bay; "Shelves, not bays" below moves the stripe, name and sticker to the shelf and keeps the sticker's own geometry. `HeavyRackRenderer` draws the label through `client/RackBeamLabel`. The rack's top front beam is only 1 px tall (y 15 to 16 between the posts), so the label is laid out around it: the zone colour stripe is a thin box over the beam's front between the posts (z 0.005 to 0.1 px out); the zone name lies below the stripe, cut with an ellipsis, left of the sticker; the code sticker is a white box hanging from the beam on the right (x 1 to 6 px, y 13.2 to 15.6 px, z 0.105 to 0.2 px), 0.005 px in front of the stripe it overlaps; its barcode bars are thin dark boxes 0.005 px in front of the sticker, maximal runs so no two bars touch, hashed from the code text by the pure `zone/Barcode` (JUnit `BarcodeTest`); the code text lies below the bars. Boxes use a plain white block texture (`textures/block/zone_sticker.png`) tinted per part. No two faces share a plane where they overlap. `FluidRackRenderer` keeps its zone name (through `client/ZoneText`, the renamed `ZoneLabelText`) and gains no sticker.

### Shelves, not bays (revised 2026-10-30)
The play check showed that zoning and coding single bays is too fine: a player thinks in shelves. Wording from now on, in text, specs and code: a **bay** is one Heavy Duty Rack or Fluid Rack block; a **shelf** is what was called a section, up to `bays_per_shelf` bays joined side by side on one level (a lone bay is a shelf of one); a **rack** is the shelves stacked over all levels and is only a word, nothing is set per rack. The shelf is the unit of the handheld and of zones: one code, one zone, one scan, one glow per shelf. Fluid Rack shelves (one tank each) follow the same model.

**Code bay.** Pure `zone/LocationCode.codeBay(List<Offset>)` takes the shelf's bays as offsets from the controller, ordered left to right seen from the front (the order `HeavyRackBlock.shelf` and `FluidRackBlock.shelf` already return), and picks the smallest squared distance dx² + dy² + dz², the first index on a tie, so the leftmost tied bay wins. On a straight shelf of whole blocks a tie cannot happen (two bays equally far from a whole-block controller always have a closer bay between them), so the tie rule only keeps the function total and deterministic. `LocationCode.ofShelf(offsets)` returns `of(...)` of the code bay. The height is part of the code, so stacked shelves differ. `HeavyRackBlock.shelf` walks from the rack's own left (its `LEFT` flag), which a viewer in front sees as the right; `ShelfZones.shelf` reverses it, so every shelf list, the shelf key and the tie rule go from the viewer's left for both rack kinds.

**Where the code lives.** `WarehouseNetwork.pushCodes` groups `codedBays` by shelf (key: the shelf's leftmost bay, from `HeavyRackBlock.shelf` or `FluidRackBlock.shelf` on the server thread), computes the code once and writes it to every bay of the shelf, with a code-bay flag on the bay that gave it (`StorageNodeBlockEntity.setLocationCode(code, codeBay)`, saved as `Code` and a new `CodeBay`, synced in the update tag). The triggers stay as they are: controller join or leave and bay join or leave. A bay joining or leaving a shelf of a warehouse always joins or leaves the network too, so no new event and no polling. The panel reads the code of whichever bay is aimed at.

**Zone storage.** The zone id stays on each bay (`ZoneId` on `StorageNodeBlockEntity`), because put-away, `WarehouseZones` and `StorageFill` work per bay and must keep working without a controller. The rule is that every bay of a shelf holds the same id, kept by one writer: new `zone/ShelfZones.set(level, pos, zone)` puts every bay of the shelf at `pos` into the zone (for Fluid Racks then calls `shelfChanged` once, replacing `FluidRackBlock.stampSection`). On a join one rule decides, in `ShelfZones.onJoin(level, placedPos)` run one tick after placing, by a scheduled block tick of `HeavyRackBlock` (NeoForge runs `onPlace`, which mirrors the join flags onto the neighbours, only after `setPlacedBy` while an item is placed, so `setPlacedBy` still sees a shelf of one) and by the Fluid Rack's settle step that already runs on its next tick: when the other bays of the shelf are zoned, the new bay takes their zone, whatever it carried; when they are unzoned and the new bay carries a zone, the whole shelf takes the new bay's zone; when neither is zoned, the shelf stays unzoned. A bay standing alone keeps the zone its item carried. This is the Fluid Rack's rule today (first zoned other bay, else the placed bay), now shared with the Heavy Duty Rack. A split needs nothing: the bays left keep their ids. A layer on top places items without a zone, so the new shelf is unzoned.
*Alternative:* store the zone only on the code bay. Rejected: the code bay moves with the controller and does not exist without one, but zones must work in a warehouse without a controller.
Counting: the zone list's "loaded shelves" counts each shelf once by its leftmost bay (`WarehouseNetwork.zoneShelfCountsById`, `HandheldActions.loadedShelfCounts`, `HandheldMenuStatePayload.shelfCounts`). Shelves with mixed zones can only exist in dev worlds of the first build; they are not migrated (nothing released) and become uniform on the next scan.

**Scans.** `HandheldActions.assign` always takes the shelf of the clicked bay; the sneak flag, the `assigned_section` message and the "Sneak: whole section" HUD hint go, and the action bar uses `assigned` with the shelf's code. `SweepTracker` gets the shelf key (leftmost bay) instead of the bay position, so moving within one shelf is the existing same-target skip and the pitch rises per shelf. FIND from a bay takes the top item over all slots of the shelf. INFO and the Data Potato share one tally: the shelf's slots (locked count as used), total and top items move out of `rack/RackReport` into `rack/ShelfStock`, used by both; a Fluid Rack's shelf handler already holds the whole tank.

**FIND result.** The server folds the bays holding the item (`network.index().sourcesHolding`) into shelves and sends one position per loaded shelf with its code. `ClientHandheld` expands each to its shelf's box once on receipt, using `HeavyRackBlock.shelf` or `FluidRackBlock.shelf` on the client level (the join flags are block state, so the client knows them), and keeps the boxes for the glow time.

**Glow and flash geometry.** A shelf's box is the union of its bays' block boxes; a shelf is a straight row on one level, so that is one box.
- Flash: the shelf box grown by 0.05 px, plus 0.005 px for each further shelf flashed at the same time.
- Glow: crossed bands along the twelve edges of the shelf box grown by `GLOW_OUT` (0.02 blocks), plus 0.005 px for each further glowing shelf. Bands along X run the full edge; bands along Y and Z stop one band width short of each corner.
- Tint: the six faces of the shelf box grown by `GLOW_OUT` minus 0.05 px (plus the same per shelf step), filled with the glow colour at low alpha, drawn like the outline with `RenderTypes.textBackgroundSeeThrough()` without depth test, for the glow time. The tint sits 0.05 px inside the bands' face planes, so the bands lie on top of it.
- Overlapping faces, listed: (1) glow and world blocks: the glow has no depth test, so it cannot fight with blocks. (2) Bands of one shelf: the two quads of one band are at right angles. Bands of edges that meet at a corner lie in the same face plane only around that corner, and there the shortened Y and Z bands end exactly where the X band's width ends, so they touch without overlapping. (3) Glow of two neighbouring shelves, side by side or stacked: their shared block face becomes two planes, `GLOW_OUT` plus the step out on each side, and their front planes differ by the step, so no band of one lies in a plane of the other. (4) Tint and the bands of the same shelf: every tint face lies 0.05 px inside the band quads of that face plane, so they never share a plane. (5) Tint faces of one shelf meet only at its edges, at right angles. (6) Tints of two neighbouring shelves: the per shelf step gives their facing faces and their front faces different planes, as for the bands; a tint of one shelf and a band of the other differ by 0.05 px plus or minus the step, never zero. (7) Flash of two neighbouring shelves: the same step gives the facing faces and the front faces different planes. (8) Flash against glow and tint: 0.05 px against 0.27 px (tint) and 0.32 px (bands) out, different planes. (9) Flash and the rack's own faces: 0.05 px off, so no shared plane. Tint and bands have no depth test, so they cannot fight with blocks either.

**Beam label per shelf.** The bays' geometry stays as in "Beam stripe and code sticker" with these changes:
- Stripe: each bay draws its piece (x 2 to 14, y 15 to 16, z 0.005 to 0.1 px). On a side joined to a neighbour in the same shelf the piece runs to the bay edge (x 0 or 16) and draws no end face, so the pieces read as one stripe. The pieces of two neighbours share their front, back, top and bottom planes but only touch along the line x 16 / x 0, with no overlapping area, and no end faces stand on that line. The beam runs through in a joined shelf (model), and the stripe's back stays 0.005 px in front of it.
- Sticker: drawn only on the code bay, with the same box and bars as before (x 9 to 14, y 13.2 to 15.6, z 0.105 to 0.2; bars z 0.205 to 0.215), so the overlap list of task 7.3 still holds. In a joined bay no post stands behind its right face at x 14, which only removes an overlap.
- Zone name: drawn once per shelf by its leftmost bay, at z 0.064 and y 13.9 to 14.9 as before, in the longer free run along the shelf: from the left inner edge (x 2 of the leftmost bay) to 0.2 px before the sticker, or from 0.2 px after the sticker to the right inner edge (x 14 of the rightmost bay); with no sticker, the whole run. It is cut with an ellipsis. Its x range never reaches the sticker, and its plane sits behind the sticker's back (0.105) and below the stripe (y under 15), so it overlaps no face. Because the leftmost bay draws across its neighbours, its renderer's bounding box covers the whole shelf (NeoForge's `getRenderBoundingBox` on the block entity renderer; check the exact 26.1.2 signature in the sources jar during apply).
- Fluid Racks get the same sticker, once per shelf on the code bay, drawn by `client/FluidRackRenderer` through `RackBeamLabel`'s sticker part with the same box and bars hanging from the top beam (x 9 to 14, y 13.2 to 15.6, z 0.105 to 0.2 px in front of the face; bars z 0.205 to 0.215; code text z 0.22). Overlap list for the Fluid Rack (`FluidRackLook`, front face at z 0, top beam y 15 to 16): sticker and top beam: the sticker's back is 0.105 px in front of the beam's front (z 0), no shared plane; sticker and glass front (z 0.9 to 1.1 behind the face) and fluid (z from 1.2 behind): z ranges disjoint; sticker and posts (front at z 0, only at shelf ends, x 0 to 2 and 14 to 16): the sticker's right face at x 14 stands in front of a post's inner face, z ranges disjoint; sticker and port flange: the flange reaches into the bay behind z 0 (check during apply that no flange face stands in front of z 0), so z ranges disjoint; bars and code text as on the Heavy Duty Rack. The zone name stays on the port bay's top beam at 0.064 px out, behind the sticker's back; when the port bay is also the code bay the name is centred in x 2 to 8.8 instead of the whole beam and cut with an ellipsis, so the sticker never covers it; on any other port bay it is centred on the whole beam (x 2 to 14) and cut the same way. `ZoneText` goes, both racks draw the name through `RackBeamLabel.name`.

**Rename section to shelf.** Player text, specs and code all say shelf. Code identifiers found by grepping `shuttles/src` for `section`:
- Classes: `rack/RackSection` becomes `RackShelf`, `rack/SectionFill` becomes `ShelfFill`, `fluidrack/FluidRackSection` becomes `FluidRackShelf`, and `fluidrack/FluidRackSectionHandler` becomes `FluidRackShelfHandler`. Their tests follow: `RackSectionTest`, `SectionFillTest` and `FluidRackSectionTest`.
- Methods: `HeavyRackBlock.section`/`sectionSize`, `FluidRackBlock.section`/`sectionSize`/`sectionFluid`, `FluidRackBlock.stampSection` (replaced by `ShelfZones.set`), `FluidRackBlockEntity.sectionHandler`/`sectionChanged`, `HeavyRackMenu.forSection`/`sectionOf`/`writeSection`, `WarehouseNetwork.readRackSection`, and `ShuttlesStatsManager.rackBaysPerSection`/`fluidRackBaysPerSection` with their `DEFAULT_*_BAYS_PER_SECTION` constants.
- GameTest names and helpers: `sneakScanTakesSection` (removed with the sneak path), `zonedSectionPreferred`, `sectionRailSetup`, `rackSectionsStayPut`, `rackSectionSharesMenu`, `rackSectionServedFromOneRail`, `rackMenuClosesWhenSectionChanges`, `rackBesideSectionNotServed`, `potatoReportsRackSection`, `onlyTheClickedSectionGetsALayer`, `oneDockedBayClosesSection`, `leftoverGoesToNextSection`, `layerCoversASectionOfThree`, `joiningDockedSectionCloses`, `frontRailConnectsSection`, `fluidRackSectionCounts`, `upperRowFollowsLowerSections`, `threeBaysOneSectionPortInMiddle`, `railsHangAlongRaisedSection`, `scanZonesSectionAndNoZoneClears`, plus `RackDockTest.sectionOfThreeWithoutRailsIsOpen`.
- Local variables, Javadoc and comments follow.
- Not renamed: "section" meaning a cross-section in `field/HarvesterParts` and `fluidstation/StationArmLook`. No saved NBT key or block state property contains "section", so worlds load unchanged.

Lang values that change (keys stay, they are not shown to players): `potato.rack_zone` "Rack shelf, zone: %s", `potato.rack_no_zone` "Rack shelf, no zone", `potato.fluid_rack_zone` "Fluid Rack shelf, zone: %s", `potato.fluid_rack_no_zone` "Fluid Rack shelf, no zone", and `gui.servus_shuttles.storage.fluid_racks` "%s Fluid Rack shelves". Removed: `message.servus_shuttles.handheld.assigned_section` and `hud.servus_shuttles.handheld.zone_hint`. A grep of `shuttles/src/main` for `ection` in lang and Javadoc must come back empty after the rename, except the cross-section hits.

**rack.json key.** The datapack key becomes `bays_per_shelf` in `rack.json` and `fluid_rack.json`. Shuttles has a tagged release, and a pack may override `bays_per_section`, so `ShuttlesStatsManager` still reads `bays_per_section` when `bays_per_shelf` is absent; `bays_per_shelf` wins when both are present. The shipped JSON files use the new key. This breaks no pack, and the old key can be dropped in a later release with a changelog line.

**Specs.** Every main spec requirement that said "section" gets a MODIFIED delta in this change (heavy-duty-rack, fluid-rack, tanker, slot-locks, storage-fill, warehouse-controller, warehouse-rail, shuttle-traffic, fluid-inbound, zones), with RENAMED headers where the name held the word. Scenario names keep "section", because OpenSpec matches a MODIFIED block's scenarios by name. Since "shelf" now names the row of bays, the spec text calls the boards inside a bay the floor board and the middle board ("Sample display" and "Boards show the crafting wood" are modified for that). The Purpose of `shuttles/fluid-rack` still says sections; it is edited by hand at archive.

### Recipe and look
Shaped recipe in datagen: iron ingots for the body, yellow dye for the bumper, a glass pane for the screen, redstone and red dye for the scan window (numbers and items in the datagen recipe, not code). Sounds are vanilla events at another pitch in `sounds.json` (`handheld.beep` note block bit, `handheld.buzz` didgeridoo, `handheld.click` stone button), played on the client from the scan and FIND answers. A 16x16 item texture: dark steel body, yellow bumper corners, green screen, red top window.

### Settles from PLAN.md
- "Zone Labels" (M6) is replaced by the handheld and team zones.
- "Wireless Terminal with range tiers" (Open: Shuttles) stays open but now names the handheld's LINK mode as its home; PLAN.md is updated at archive.

### Pure vs Minecraft
Pure with JUnit: `ZoneList` (names, uniqueness, ordering, search, resolve), `LocationCode` (format and the code bay of a shelf), the sweep tracker (same shelf skip, count reset), `TagSearch` (tag matching and order). Minecraft side with GameTests: assigning a shelf from any bay, sweep across shelves, Fluid Rack shelf, a bay joining a shelf taking its zone, a split shelf keeping its zone, zone edit changing put-away, delete unzoning shelves, old `Zone` tag loading unzoned, shelf codes after the controller moves and after a shelf loses its code bay. Manual play check: panel, sounds, sweep feel across shelves, shelf flash, shelf glow, beam stripe and sticker without flicker, the device GUI with its CRT, softkeys and green icons, INFO only after a scan, and the zone filter picker with `#` tag completion.

## Risks / Trade-offs

- [Removing the Zone Label breaks worlds that used it] → Accepted with the user; the changelog says zones must be set again.
- [Held-use repeat at 4 ticks may feel slow on a fast sweep and skip a bay] → The sweep checks the crosshair target at each repeat; if play tests show skipped bays, the client can send the bays between the last and the current hit along the row.
- [Broadcasting `ZonesEdited` to every warehouse network] → Edits are rare player actions; each network only rebuilds its zone tiers.
- [Codes change when the controller moves] → Intended; the code is relative by design. A shelf's code can also jump to another of its bays when the controller moves or the shelf loses its code bay; the sticker moves with it.
- [The zone id is stored per bay but must be equal across a shelf] → One writer (`ShelfZones.set`) and the join rule keep it uniform; GameTests cover join, split and layer.
- [Renaming `section` touches many files and GameTest names] → Done as one mechanical task with no behaviour change, after the shelf behaviour is green, so a failing test points at one or the other.
- [The green overlay on icons is an approximation, not a true tint] → Reads as phosphor at icon size; the hovered item in full colour keeps items recognisable.
- [Text on the beam gets crowded with a long zone name and a code] → Names are capped at 24 characters and cut with an ellipsis on the beam; the full name is in the GUI title and the panel.

## Migration Plan

No data migration. On load, racks ignore the old `Zone` tag and the Zone Label item is unregistered, so stacks of it are dropped by the game. Rollback is not supported for worlds saved with team zones on an older version (they would load unzoned there too).
