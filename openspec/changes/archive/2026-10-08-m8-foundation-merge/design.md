# Design

## Context

Four Gradle projects today: `lib` (`servus_lib`, API plus carrot, goggles and since `m8-data-cable` the Data Cable), `logistics` (`servus_logistics`, Utility Duct, Fluid Tank, facades), `manufacturing` (depends on both) and `storage` (depends on `lib`). Shared build logic lives in the root `build.gradle` (`subprojects` block, metadata expansion with `lib_version_range` and `logistics_version_range`, combined `clientAll`, `serverAll`, `gameTestServerAll` runs). Each mod has its own `@Mod` entry class, datagen subscriber, GameTests and resources namespace. See proposal.md for why.

The open change `m8-data-cable` already put its code into `lib` (package `lib.data`) and its delta into `specs/lib/data-cable`.

## Goals / Non-Goals

**Goals:**
- One mod `servus_foundation` with the union of Lib and Logistics, behavior unchanged, all tests green under the new ids.
- API and content stay apart inside the mod, so other mods can rely on the API packages.
- Everything that names the family (plan, rules, docs, CI) says three mods.

**Non-Goals:**
- Changing the Data Cable (follow up in `m8-data-cable`).
- Registry aliases or other compatibility for old ids.

## Decisions

### Gradle
- `git mv lib foundation`; `settings.gradle` includes `foundation`, `manufacturing`, `storage`. `foundation/gradle.properties`: `mod_id=servus_foundation`, `mod_name=Servus: Foundation`, a description covering API, ducts, tanks and tools.
- Logistics sources, tests and resources move into `foundation/src`; `logistics/` is deleted, including its `build.gradle` and run directory.
- Root `build.gradle`: `allServusMods` is `foundation`, `manufacturing`, `storage`; the metadata expansion offers `foundation_version_range` and drops the two old ranges; Manufacturing's data run reads generated resources from `foundation`, `manufacturing` and `storage` and its `runData` must run after `:foundation:runData`.
- `manufacturing` and `storage` use `compileOnly project(':foundation')` and `loadedMods = [ownMod, foundationMod]`.
- Foundation's runs get the dev conveniences Logistics had (none today) and keep `enabledGameTestNamespaces = servus_foundation`.

### Packages and class names
- `io.github.dirnei.mc.servus.lib.*` becomes `io.github.dirnei.mc.servus.foundation.*` with the same sub packages (`network`, `graph`, `production`, `data`, `side`, `placement`, ...). This is the API part.
- `io.github.dirnei.mc.servus.logistics.*` becomes `io.github.dirnei.mc.servus.foundation.logistics.*` with its sub packages (`duct`, `tank`, `facade`, `routing`, `menu`, `client`, `datagen`, `gametest`, `network`, `registry`). Putting content one level down avoids clashes with the API packages of the same name (`client`, `datagen`, `network`, `registry`) and keeps API and content apart.
- One `@Mod` class `ServusFoundation` (was `ServusLib`) with `ServusFoundationIds.MOD_ID = "servus_foundation"`. The old `ServusLogistics` entry becomes `logistics/ServusLogisticsContent` with a static `register(IEventBus)` called from the `ServusFoundation` constructor; `ServusLogisticsIds` is removed in favour of `ServusFoundationIds`. Lib classes named `ServusLib*` are renamed `ServusFoundation*`; Logistics registry classes keep their `ServusLogistics*` names (a second `DeferredRegister` per registry for the same namespace is supported by NeoForge).
- `@EventBusSubscriber(modid = ...)`, `@GameTestHolder(...)` and payload registrars use `ServusFoundationIds.MOD_ID`.
- Manufacturing and Storage imports are rewritten mechanically (`servus.lib.` to `servus.foundation.`, `servus.logistics.` to `servus.foundation.logistics.`, class renames).

### Datagen
Two `GatherDataEvent` subscribers for one mod would register two providers of the same kind and name (language `en_us`, block states, block tags, loot tables, recipes) and fail with duplicate providers or overwrite each other's files. So there is one `ServusFoundationDataGen` that registers one provider per kind; each provider calls an `add...` helper per part (API items, Data Cable, Logistics content). The Logistics helpers (`DuctPartModels`, `FluidTankModels`) stay as they are.

### Resources
`assets/servus_lib`, `assets/servus_logistics` and `data/servus_logistics` (`duct`, `tank`, GameTest `structure`) move to `servus_foundation`. Lang keys, model and texture references, recipe ids and translation keys with `servus_lib.` or `servus_logistics.` get the new prefix; Manufacturing and Storage code that uses Lib lang keys (`gui.servus_lib.side.*`) follows. `src/generated/resources` of both old projects are deleted and regenerated by `:foundation:runData`.

### Specs and planning files
- `git mv openspec/specs/lib/* openspec/specs/foundation/` and `openspec/specs/logistics/* openspec/specs/foundation/` (no name clashes: lib has 13 capabilities, logistics 4, all different). Each moved spec's title line and Purpose naming Lib or Logistics as owner are edited directly; requirement text is changed only through this change's deltas. The deltas here target the new paths, so the move must happen before archive (OpenSpec refuses MODIFIED on a missing spec).
- `openspec/changes/m8-data-cable/specs/lib/data-cable` moves to `.../specs/foundation/data-cable`.
- PLAN.md: section 1 table and dependency text, repository layout, 2.2 becomes "Servus: Foundation", 2.3 and 2.4 drop "Storage stays independent of Logistics", section 3 "Servus Lib API" becomes "Servus: Foundation API", M8 gets `m8-foundation-merge` first and `m8-data-cable` described as the Data line of the duct. Earlier milestones keep their historical wording.
- CLAUDE.md and `openspec/config.yaml` context: three projects, mod ids, the new dependency rule.

### Docs and CI
- `docs/src/content/docs/mods/lib.md` and `logistics.md` become one `foundation.md`; sidebar config follows; `gamedata.json` is regenerated by Manufacturing's data run; docs tests that name ids are updated; `npm test` in `docs/` stays green.
- `.github/workflows/build.yml` collects jars from `foundation/build/libs`.

### Verification
JUnit (all projects), GameTests per project (`:foundation:runGameTestServer` now runs the former Logistics tests, plus `:manufacturing:` and `:storage:`), `runClientAll` and `:foundation:runClient` reach the title screen, a grep finds no `servus_lib`, `servus_logistics`, `servus.lib.` or `servus.logistics.` outside history (archived changes) and docs build output.

### PLAN.md open decisions
Settles the family layout: three mods, Foundation as the shared base. Nothing in section 5 is affected.

## Risks / Trade-offs

- [A huge mechanical rename hides a missed reference] -> after the rename, grep for the old ids and package names must come back empty (outside archives), and every GameTest suite runs.
- [Datapack JSON loaders that filter by namespace] -> checked during the move: loaders that look for `servus_logistics` paths are switched to the Foundation namespace and the duct and tank tests cover them.
- [Dev worlds lose old blocks] -> accepted, nothing is released; the user is told before the merge lands.
- [Helper scripts outside the repo (`g.sh`, `run_server.sh`) list the old projects] -> updated in the session helpers; not part of the repo.
- [`runs/` of the old projects hold eula and RCON settings] -> `foundation/runs/server` gets `eula.txt` and the RCON `server.properties` copied from `logistics/runs/server`.
- [Foundation now carries content, so an API user pulls in ducts] -> accepted by the user; the API packages stay separate so a split jar stays possible later.
