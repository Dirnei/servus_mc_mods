# Design

## Context

See proposal.md for motivation. Today `servus_lib` registers `WrenchItem` under the id `wrench` with `stacksTo(1)`, a `basicItem` model over `textures/item/wrench.png`, a shaped recipe and lang entries, all generated by the Lib datagen providers into `lib/src/generated/resources`. Blocks opt in through the `Wrenchable` interface, and seven block classes across all four mods test `stack.getItem() instanceof WrenchItem` to skip their GUI or default interaction. `GogglesItem.reveals` uses the same check for the duct overlay. `ServusLibConfig` keeps the `wrench.wrenchRotatesBlocks` option.

## Goals / Non-Goals

**Goals:**
- Replace the player facing wrench item completely: id, name, texture, recipe, tab icon.
- Keep every behavior and every block side API untouched so content mods only touch imports.
- Keep the change small enough for one session, with datagen regenerating all data files.

**Non-Goals:**
- Any change to how `Wrenchable` blocks react. No new interaction.
- A new art style for other items. Only the carrot texture is new.

## Decisions

### Rename the item class, keep the role interface
`WrenchItem` becomes `ConfigurationCarrotItem` in the same `lib.item` package. `Wrenchable` and `onWrench` keep their names. Rationale: the interface names the role a block plays, and the specs of machines, ducts and storage blocks speak of "the wrench" as that role. Renaming it would touch every content mod block and six main specs for no behavior change. Alternative considered: keep `WrenchItem` as the class name too. Rejected, because an item class named wrench for an item with id `configuration_carrot` confuses every future reader, and the import change in the seven block classes is trivial.

### PLAN.md wording
PLAN.md section 5 leaves no open decision about the tool, so this change settles none. It updates the PLAN.md Lib row, the two wrench bullets in section 2.2 and the M1 item "Wrench item" to say "Configuration Carrot (the wrench role)". No other plan text changes.

### Registration and datagen
- `ServusLibItems.CONFIGURATION_CARROT`: `ITEMS.registerItem("configuration_carrot", ConfigurationCarrotItem::new, new Item.Properties().stacksTo(1))`. No food component, so the item is never edible. Same `DeferredRegister.Items.registerItem` call the wrench uses today in `ServusLibItems`.
- Item model: `basicItem(ServusLibItems.CONFIGURATION_CARROT.get())` in `ServusLibItemModelProvider`, which points at `textures/item/configuration_carrot.png`.
- Recipe in `ServusLibRecipeProvider` with `ShapedRecipeBuilder.shaped(RecipeCategory.TOOLS, ...)`, pattern `"R"`, `"I"`, `"C"` with `Items.REDSTONE`, `Items.IRON_INGOT`, `Items.CARROT`, unlocked by `has(Items.CARROT)`. The vertical column mirrors the icon: red tip, metal bar, carrot. The old wrench recipe is deleted. Datagen removes its JSON and advancement on the next `:lib:runData` because the generated folder is rewritten.
- Lang in `ServusLibLanguageProvider`: item name "Configuration Carrot", config texts "Configuration Carrot" and "Configuration Carrot rotates blocks". Lang keys `servus_lib.configuration.wrench` and `servus_lib.configuration.wrenchRotatesBlocks` stay with the TOML keys.
- Creative tab icon and entry in `ServusLibCreativeTabs` switch to the new holder.
- Config comment in `ServusLibConfig` says "the Configuration Carrot" instead of "the wrench". Key names unchanged, the role is still called wrench in code and config.

### Texture
A 16 by 16 PNG hand pixelled with a throwaway Python script in the scratchpad that writes the PNG with `zlib` and `struct`, no Pillow dependency. Palette: three orange shades for the carrot body with darker lines for the carrot grooves, two greys for the metal bar, two reds for the tip, transparent background. Layout: carrot body diagonal from bottom left to upper right like the vanilla carrot, the metal bar continues the carrot axis for about three pixels, the tip is the last one or two pixels. No green pixels anywhere. Only the PNG is committed, the script is not. The old `wrench.png` is deleted.

### Content mod updates
Each block class that does `instanceof WrenchItem` changes the import and the check to `ConfigurationCarrotItem`: `ConnectableBlock` in lib, `MachineBlock` in manufacturing, `UtilityDuctBlock` in logistics, `WarehouseControllerBlock`, `CrateBlock`, `RackBlock` and `CounterTerminalBlock` in storage. `GogglesItem.reveals` likewise. Alternative considered: a static `ConfigurationCarrotItem.isHeld(ItemStack)` helper so blocks stop naming the class. Rejected for now, it adds API surface the proposal does not need.

### Spec purpose text
The main spec `openspec/specs/lib/wrench/spec.md` keeps its capability path. Its Purpose is edited directly during apply to say that the Configuration Carrot is the item that fills the wrench role and that other specs use "wrench" for that role. Delta specs cannot carry a purpose change, so this edit is a task.

## Pure versus Minecraft logic

Everything in this change touches Minecraft registries, datagen or rendering. There is no new pure Java logic and no new JUnit test. Verification is datagen output, a full build, the GameTests already in the repo (they compile against the renamed class and use the tool through the `Wrenchable` path) and a manual client check of texture, recipe, tab and reveal overlay.

## Risks / Trade-offs

- [Dev worlds lose their wrenches] -> Fine, nothing is released and the dev world is disposable.
- [Stale generated files linger if datagen is not run] -> `gradlew :lib:runData` is part of the first task group and the build fails on the missing texture reference otherwise.
- [A green pixel sneaks into the texture] -> The texture task checks the PNG palette has no pixel with a dominant green channel before committing.
