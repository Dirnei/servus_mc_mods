# Design

## Context

See proposal.md for motivation. The warehouse network is `WarehouseNetwork`, a `ServusNetwork` over `StorageNodeBlockEntity` nodes with `ConnectionRule.always()`, so any two touching nodes are connected by the Lib graph. Every node added today becomes an indexed source with a `BlockCapabilityCache`, and `addCandidatesAround` and `rebuildCandidates` turn all six neighbours of every member into foreign source candidates. Lib has `ConnectableBlock`, a `BaseEntityBlock` with six boolean connection properties, placement and shape update logic, a cached voxel shape built from a centre cube and arms, Configuration Carrot handling and sneak dismantle. `ConnectableModels` writes the matching multipart blockstate for cube shaped connectables. Storage blocks are registered in `ServusStorageBlocks`, `ServusStorageItems` and `ServusStorageBlockEntities`, with datagen providers for blockstates, lang, recipes, loot and tags and a GameTest class using the `empty_12x6x12` template.

## Goals / Non-Goals

**Goals:**
- Rails join the existing graph without touching Lib. One new node kind, no new network type.
- Rails never cost index work: no source, no capability cache, no polling.
- A flat rail look that reads as a track, generated by datagen like every other model.

**Non-Goals:**
- Shuttle paths, directions or speeds. The rail stores no routing data yet.
- Changing how adjacency works for the existing blocks.

## Decisions

### Settles the PLAN.md open decision on rail design
Floor rails only, one block wide, auto connecting on the same level like ducts, no slopes. Chosen by the user on 2026-10-06 over ceiling rails and over separate straight and curve pieces. PLAN.md section 5 drops the "Exact rail block design" bullet and section 2.3 states the decision.

### Rail block extends ConnectableBlock
`RailBlock extends ConnectableBlock` with radius 3. `connectsTo` returns true only for horizontal directions whose neighbour is a `RailBlock`, so `UP` and `DOWN` stay false and rails stacked vertically do not link visually. `getShape` is overridden to a flat box, `Block.box(0, 0, 0, 16, 2, 16)`, ignoring the parent's cube shape, so players walk over rails. `canSurvive` requires `canSupportRigidBlock` below, like vanilla rails, and `updateShape` from the parent keeps the connection flags fresh; the block entity type comes from `newBlockEntity`. Alternative considered: a standalone block with four properties. Rejected, it duplicates placement, shape update and dismantle code that `ConnectableBlock` already has.

The graph connection is separate from the visual flags: the network uses `ConnectionRule.always()`, so a rack touching a rail from above or beside is in the network even though the rail shows no arm towards it. That matches the spec: storage blocks touching a rail on any side join.

### Rail block entity is a connector node
`RailBlockEntity extends StorageNodeBlockEntity` and overrides a new method `boolean holdsStock()` to return false. `StorageNodeBlockEntity.holdsStock()` defaults to true, so crates, racks, controller and terminal keep today's behaviour. `WarehouseNetwork`:
- `onNodeAdded`: when `holdsStock()` is false, record the position in a `connectors` set and skip `addSource` and `addCandidatesAround`.
- `onNodeRemoved`: remove from `connectors`, then `rebuildCandidates` as today.
- `onAbsorb`: merge the other network's `connectors`.
- `onDisposed`: clear it.
- `rebuildCandidates` and `addCandidatesAround` compute wanted neighbours only around stock holding members. `handle(NeighborsChanged)` ignores positions in `connectors`.
- `summary()` adds the rail count.

Alternative considered: a second network type for rails bridged through the controller. Rejected, one graph with a flag is far simpler and the always rule already gives the connectivity.

### Split handover in Lib
Found during the GameTest: `NetworkSet.apply` creates networks for split off components without telling them about their members, and the surviving network keeps the sources, endpoints or caches of nodes that moved away. The warehouse part cut off by a broken rail therefore had no level and crashed on chunk unload, and the same gap left duct and cable networks dead after a cut. `NetworkSet` gets a private `handOver(old, change)` that runs after `apply` in `nodeRemoved` and `nodeRefreshed`: for each created component it calls `old.onNodeRemoved` and `created.onNodeAdded` for every member. The refreshed node is always in the survivor, so it is never handed over twice. All five content networks only put and remove per node entries in those hooks, so they need no change. Alternative considered: a new `onSplit` hook. Rejected, the existing hooks already express leave and join and every network implements them.

### Pure candidate computation
The neighbour set logic of `rebuildCandidates` moves into `io.github.dirnei.mc.servus.storage.index.CandidateNeighbours`, a final class with one static method `Set<NodePos> compute(Set<NodePos> members, Set<NodePos> connectors)`: for each member that is not a connector, add its six neighbours that are not members. `NodePos` lives in Lib's pure graph package, so the helper has no Minecraft imports. `WarehouseNetwork` converts with `Conversions` as it already does. JUnit: `CandidateNeighboursTest` covers a single member, two touching members sharing a neighbour, a connector between two members whose own neighbours are excluded, and a connector only network giving an empty set.

### Datagen and look
A storage side helper `RailModels` in the storage datagen package writes a multipart blockstate: a centre plate model `rail_center` (`from(5, 0, 5).to(11, 1, 11)`), an arm model `rail_arm` (`from(5, 0, 0).to(11, 1, 5)`) rotated 0, 90, 180 and 270 for north, east, south and west on the matching `ConnectableBlock` property, plus a `rail_inventory` model that is a full straight piece for the item. All faces use one texture `block/rail`. `ConnectableModels` stays untouched because its elements are cubes. The texture is a 16 by 16 placeholder drawn by a scratchpad script: two grey rails on dark sleepers, matching the rest of the placeholder art.

### Registration and data
- `ServusStorageBlocks.RAIL`: id `rail`, `MapColor.METAL`, strength 1.0, `SoundType.METAL`, `noOcclusion()`.
- `ServusStorageItems.RAIL` as a simple block item, appended to `CREATIVE_TAB_ORDER`.
- `ServusStorageBlockEntities.RAIL` for `RailBlockEntity`.
- Recipe in `ServusStorageRecipeProvider`: pattern `"III"`, `" S "`, `"III"`, iron ingots and a stick, output 8, category `RecipeCategory.DECORATIONS`, unlocked by having an iron ingot. The amount is an example; it lives in the generated JSON, not in logic.
- Loot: self dropping in `ServusStorageBlockLoot`. Tags: `MINEABLE_WITH_PICKAXE`.
- Lang: "Warehouse Rail".

### GameTest
`railsLinkCrateAndController` in `ServusStorageGameTests` on the `empty_12x6x12` template: crate at (2,1,3), rails at (3,1,3) and (4,1,3), controller at (5,1,3), terminal at (6,1,3), a chest with bread at (3,1,4) touching only the rail. After 10 ticks the terminal menu stock is online, lists the crate's cobblestone and does not list bread. Then the rail at (3,1,3) is removed and after 10 more ticks the stock no longer lists cobblestone.

## Pure versus Minecraft logic

Pure: `CandidateNeighbours` with JUnit. Minecraft: `RailBlock`, `RailBlockEntity`, `WarehouseNetwork` membership changes, datagen and the GameTest. The rail look and walkability are checked manually in the client.

## Risks / Trade-offs

- [Rails create many block entities] -> Each rail block entity is tiny and ticks nothing. Ducts already do the same in Logistics.
- [A rack touching a rail only from below or above joins without a visible arm] -> Accepted and specified. The overlay from goggles is not needed because rails are visible.
- [Breaking a rail splits the network and the Lib graph must rebuild] -> Already handled by the split logic the ducts rely on. The GameTest covers the removal case.
- [Chest beside a rail that also touches a rack] -> Candidates come from stock holding members, so the rack brings the chest in. Covered by a scenario and the JUnit test.
