# Design

## Context

The Heavy Duty Rack already shows the wood of its recipe (archived m6-rack-wood-material): a `servus_storage:rack_wood` component holding a planks block id, a `ShapedRecipe` subclass that records the wood, a block entity that keeps it in NBT, the update tag and its model data, and `HeavyRackModel`, an `IDynamicBakedModel` wrapper installed in `ModelEvent.ModifyBakingResult` that swaps every quad textured with a board marker sprite for the planks block's particle sprite (UV remapped per vertex). No texture per wood. The eleven blocks of this change are plain textured cubes (`orientable`, `cube`, `cubeAll`) with per state front textures; most have block entities with different base classes. The CPU already stores its position in the cube as `PART` (0..26, `x + 3z + 9y`) while `FORMED`.

## Goals / Non-Goals

**Goals:** one reusable wood material for many blocks across Foundation and Storage; the rack style on eleven blocks; a connected formed CPU with animated lights; Pattern Storage lights; no texture per wood.

**Non-Goals:** porting the rack to the shared material; a single wood per formed cube; per face connected textures beyond the CPU.

## Decisions

### D1. Shared wood material in Foundation (`foundation.wood`)
- `WoodPick` (pure, JUnit): the rack's rule, most frequent id, tie by middle entry.
- `ServusFoundationComponents.WOOD`: `servus_foundation:wood`, a `ResourceLocation` with codec and stream codec.
- `WoodRecipe extends ShapedRecipe` with serializer `servus_foundation:wood_shaped` that reuses the shaped codecs (datagen and JEI see a shaped recipe); `assemble` records the picked planks id. Datagen saves recipes through an output wrapper that rewrites the type, like the rack.
- `WoodSlot`: a small helper a block entity owns. It reads and writes the component (`applyImplicitComponents`, `collectImplicitComponents`), NBT key `Wood`, the update tag, requests a model data update on the client when it changes, and builds `ModelData` with `Wood.PROPERTY`. `Wood.of(stack)`, `Wood.or(id)` return oak for missing or unknown ids. `Wood.stamp(ItemStack, BlockEntity)` copies the wood onto a dismantle drop.
- `WoodBlockItem extends BlockItem`: tooltip line with the planks block name.
- Client `WoodModel implements IDynamicBakedModel`: the generic form of `HeavyRackModel` with the marker `servus_foundation:block/wood_board`; item models resolve through `ItemOverrides` per stack wood. `WoodModels.register(Block)` collects the block ids; one `ModifyBakingResult` handler in Foundation wraps every model whose id is a registered block (block state variants and the inventory model).

### D2. Layered models, no texture per wood
Each restyled face is two coplanar elements in one model: a full cube with the board marker on every face, then a full cube with a cutout overlay texture per face (iron frame, rivets, screens, lamps; transparent where boards show). Vanilla `grass_block` uses the same coplanar overlay. The model sets `render_type` cutout. A datagen helper `LayeredModels` in Foundation builds these from face textures (`orientable` style: front, side, top; `cube` style: six faces). Quads of the overlay keep their sprites; only board quads are retextured, so lamps and screens stay teal.

### D3. Textures
Generated by Python helpers in the session helpers dir from the rack palette (iron base 40 to 49 grey, light rim top and left, dark rim right and bottom, rivets with a 0x5c highlight). One overlay per face and state, keeping today's texture names where possible so the blockstate logic stays. The board marker is an oak look copy of the rack board.

### D4. Connected CPU
`CpuBlock` gains `ACTIVE`. While formed, the model of a block depends on `PART` and `ACTIVE`: per face the tile is chosen from the block's offset in the cube by the pure `CpuTiles` (JUnit), which knows for each face which world directions are the texture's left, right, top and bottom under vanilla's default UVs (north: left is east; south: left is west; west: left is north; east: left is south; up: top is north, left is west; down: top is south, left is west). A tile is named by its frame sides (`top`, `bottom`, `left`, `right` combinations), nine tiles per active state, with lights inside. Overlay tiles are animated with `.png.mcmeta`: active tiles run (frametime 2, 8 frames), idle tiles glow slowly (frametime 10, 8 frames). Faces toward the inside of the cube are culled by neighbours and get the center tile. Unformed blocks use a riveted casing overlay. 27 parts times 2 states give 54 formed models plus one casing model.
The master sets `ACTIVE` on all 27 blocks when its order book reports a change and the open count crosses zero (`Host.changed()` and load), never per tick.

### D5. Pattern Storage lights
`PatternStorageBlock` gains `LIGHTS` (0..9). `PatternLights.lit(stored, capacity)` (pure, JUnit) scales to 9 and rounds up while any pattern is stored. The block entity updates the state on save, delete, load and placement. Ten front overlays, one per count, generated with lights in reading order.

### D6. Recipes
Every listed recipe contains planks; recipes without planks replace their bottom row with planks: Access Point `IRI/OCO/PPP`, Inbound Station `III/ICI/PHP`, Outbound Station `ICI/IDI/PHP`, Production Terminal `GGG/CMC/PRP`, Pattern Storage `IAI/RCR/PPP` (A paper), Crafting Station `ITI/ICI/PPP`, Crafting CPU `IRI/RCR/PPP` (4), Machine Adapter `CHC/RDR/PPP`. Counter Terminal, Warehouse Controller and Shuttle Garage already have planks.

### D7. Drops
Loot tables of the eleven blocks copy `servus_foundation:wood` from the block entity (Pattern Storage also copies its patterns). Dismantle paths that build `new ItemStack(this)` call `Wood.stamp`; paths using `saveToItem` already carry components.

### APIs
NeoForge 21.1.255: `IDynamicBakedModel`, `ModelData`/`ModelProperty`, `ModelEvent.ModifyBakingResult`, `IQuadTransformer.STRIDE/UV0`, `BlockEntity.applyImplicitComponents/collectImplicitComponents`, `CopyComponentsFunction`, NeoForge model `render_type`. Vanilla `BlockElement` default UVs (`uvsByFace`) for D4.

### PLAN.md open decisions
None settled; this is polish on M8 blocks.

### Pure vs Minecraft
- Pure, JUnit: `WoodPick`, `CpuTiles`, `PatternLights`.
- GameTests: recipe assembly records the wood, a placed birch item makes a birch block entity and the drop keeps it, dismantle keeps it, CPU parts and `ACTIVE` follow forming and orders, Pattern Storage `LIGHTS` follows saves and deletes.
- Manual: the look of every block and item, animation, particles.

## Risks / Trade-offs

- [Coplanar overlay z-fighting] -> same vertices and the overlay drawn after the board in one model, as vanilla grass does; if a GPU shows flicker the overlay can be inset by 0.01 later.
- [Model count] -> about 55 CPU models plus a few per block; quads are cached per wood and state in the wrapper and dropped on reload.
- [Mixed woods in one CPU] -> accepted, recorded for the user.
- [Existing worlds] -> placed blocks without wood show oak.
