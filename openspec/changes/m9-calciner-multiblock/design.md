# Design

## Context

See proposal.md for the why. Today `CalcinerBlock` is a `MachineBlock` and `CalcinerBlockEntity` a `BurnerMachineBlockEntity` with a two slot inventory, `PrincipleTanks`, a `TeamOwnership`, side configuration with a Fluids layer (`sideTanks()`, `AlchemyMachines.sideHandler/push`), a menu (`CalcinerMenu`, `CalcinerScreen`) and capabilities registered per block entity in `ServusManufacturingEvents` (item, upkeep, fluid). The Sink (`foundation/machine/sink`) is the only multiblock in the project: its own blocks carry `FORMED`, `FACING` and `PART` in their block state, and it is formed with the carrot.

Modonomicon 1.120.7 (checked in the jar): `MultiblockDataManager` is a server side `SimpleJsonResourceReloadListener` over `data/<ns>/modonomicon/multiblocks`, synced to clients with `SyncMultiblockDataMessage`; `ModonomiconAPI.getMultiblock(id)` reads it. The dense format is `pattern` (layers top to bottom) plus `mapping`, with `0` as the required center, `_` as any block and space as air. Datagen: `MultiblockProvider` with `DenseMultiblockBuilder`; the book page is `BookMultiblockPageModel.withMultiblockId(...).withVisualizeButton(true)`.

## Goals / Non-Goals

**Goals:**
- One source for the layout: the pure `CalcinerLayout` drives forming, part lookups and the generated Modonomicon JSON.
- Formed blocks are drawn as chunk baked model pieces, and only the moving bits (fill levels) go through a block entity renderer.
- No scanning: forming is a click, unforming reacts to block removal.

**Non-Goals:**
- A shared multiblock framework for the Coagulator and the Athanor. Their changes may extract one from this code once there is a second user.

## Decisions

### Layout (pure Java)
`manufacturing/alchemy/calciner/CalcinerLayout` has no Minecraft imports. It defines the cells as `(right, up)` offsets from the Calciner in the front plane (depth 0) and a `Role` enum: `CALCINER (0,0)`, `BRICK (-1,0) (1,0) (-1,-1) (1,-1) (-1,-2) (1,-2)`, `FIREBOX (0,-1)`, `ASH_PAN (0,-2)`, `ALEMBIC (0,1)`, `RECEIVER (1,1)`, `HOOD (0,2)`. A `Facing` enum (N, E, S, W) maps `right` to x/z the same way the project already does for relative sides (left and right are the player's when looking at the front: facing north, right is west). API: `cells()`, `worldOffset(cell, facing)`, `controllerOffset(role index, facing)`, `roleAt(offset, facing)`. Plain `int` triples, no `BlockPos`.

JUnit `CalcinerLayoutTest`: cell count and roles, round trip for every cell and facing, right of the Alembic is the Receiver for every facing, free corners are not cells.

### Forming with our own check, not `Multiblock.validate`
Forming walks `CalcinerLayout` over the four facings and compares blocks; it keeps the facing with the most matching cells to name the first wrong block. `Multiblock.validate` was the alternative: it returns the rotation but cannot say what is missing, and a datapack could change the JSON away from the fixed model. The Modonomicon JSON is generated by a `MultiblockProvider` that reads `CalcinerLayout`, so the book shows exactly what forming checks. The `0` center is the Calciner; `_` marks the free corners.

### Block states and the shell block
- Custom parts (`CalcinerPartBlock` with a `Role`): `Firebox`, `AshPan`, `Alembic`, `Receiver`, `SulfurHood`. State: `FORMED`, `FACING`; the Firebox also has `LIT`.
- The Calciner block keeps id `calciner` and gains `FORMED` (it already has a facing from `MachineBlock`).
- Vanilla Bricks cannot carry state, so forming replaces each brick cell with `calciner_shell` (state `FACING`, `CELL` 0..5). It looks like bricks in item form never: it has no item, drops `minecraft:bricks`, has the bricks' hardness and tool, and `isFormed` is implied. Unforming sets it back to `minecraft:bricks`. This is the Immersive Engineering approach; the alternative, a custom Calciner Brick item, was rejected because the user wants vanilla blocks where they fit.
- Every part finds the Calciner from its own position, role (or `CELL`) and `FACING` via `CalcinerLayout.controllerOffset`. Parts have no block entity.

### Unforming
`onRemove` of any formed block (shell, part or Calciner) where the new state is not the same block calls `CalcinerStructure.unform(level, controllerPos, facing, brokenPos)`: shells become Bricks, parts and the Calciner get `FORMED=false`, the broken position is skipped. Explosions and pistons go through `onRemove` too (formed blocks also get `PushReaction.BLOCK`). Whether the Calciner is formed and which way it faces live only in the block states (`FORMED`, `FACING`), which the chunk saves; the block entity reads them from its own state instead of keeping a copy that could disagree. Server thread only.

### Interaction
`CalcinerBlock.useItemOn`:
- holding `ParacelsusJournalItem`: form (or report), `InteractionResult.SUCCESS` so the item's `use` (open the book) is not called. On success the clicking player becomes the owner (`setOwner`, team as today).
- holding the Configuration Carrot: `ItemInteractionResult.FAIL` on every Calciner block, so `MachineBlock`'s carrot path (side cycle, dismantle) never runs.
- formed and holding a calcinable item: insert into `SLOT_INPUT`.
- `useWithoutItem` sneaking and formed: give the input back. Never open a menu.
`FireboxBlock.useItemOn` inserts fuel. Port blocks fill an empty container with `FluidUtil.tryFillContainer` from their principle's tank (`IFluidHandlerItem` path, as the current gauge buttons use).

### Capabilities by position
Registered with `RegisterCapabilitiesEvent.registerBlock` (verified in NeoForge 21.1.255) on the part and Calciner blocks, resolving the Calciner block entity through the layout and returning null while unformed:
- `ItemHandler.BLOCK`: Calciner block gives an insert only view of `SLOT_INPUT`; Firebox an insert only view of `SLOT_FUEL`.
- `UPKEEP`: Firebox only.
- `FluidHandler.BLOCK`: Ash Pan Salt, Receiver Mercury, Hood Sulfur, each a drain only single tank view of `PrincipleTanks`.
The block entity registrations for item, fluid and upkeep on the Calciner block entity type are removed. The push every 10 ticks stays but pushes each tank from its own port block into its six neighbours, skipping the structure's own blocks.

### Side configuration and GUI removed
`CalcinerBlockEntity` stays a `BurnerMachineBlockEntity` for the fuel and progress logic. It returns an empty `sideTanks()`, locks all item sides Off and `createMenu` is gone; `CalcinerMenu`, `CalcinerScreen`, the menu type and the screen registration are deleted. `canWork()` also requires `formed`.

### The formed model
- Each formed block uses a `formed` blockstate variant pointing at its piece of the big model (`block/calciner/formed/<cell>`), rotated by `FACING`. Pieces may overhang into neighbour cells within the vanilla -16..32 element limit, so the whole reads as one furnace with a copper alembic and pipe to the receiver. Unformed parts have their own small models. Pieces are written as model JSON in datagen or by hand under `src/main/resources`; final art can replace them later.
- Dynamic parts in `CalcinerRenderer` (BER on the Calciner block entity, `getRenderBoundingBox` from `IBlockEntityRendererExtension` covering the 3x5 box, as `SinkRenderer` does): the Salt heap height in the Ash Pan, the Mercury level in the Receiver flask and the Sulfur crust in the Hood, drawn as fluid textured boxes scaled by fill. Fill is synced with the block entity update packet when it changes by a visible step.
- Fire: Firebox `LIT` state for the emissive coal texture and light level 13; `animateTick` on the Firebox (flames) and Hood (smoke) when lit.

### Journal
`WorkshopCategory.calciner()` gains a multiblock page for `servus_manufacturing:calciner` with Visualize, crafting pages for each part and text about forming with the Journal. Text that mentions gauges and the GUI is rewritten. A new `ServusManufacturingMultiblockProvider` is added to the data generators.

### Jade
A `CalcinerJadePlugin` (`@WailaPlugin`) registers an `IServerDataProvider<BlockAccessor>` and `IBlockComponentProvider` for the Calciner, part and shell block classes, reading the Calciner block entity through the layout. Jade 15.10.6 is added as `compileOnly` in `manufacturing/build.gradle` (it stays `localRuntime`). Classes are only loaded by Jade, so Manufacturing runs without it.

### Recipes (examples, datagen)
- Calciner: bricks, iron bars, cauldron.
- Firebox: bricks around a furnace with iron bars.
- Ash Pan: iron ingots and bricks.
- Alembic: copper ingots and glass.
- Receiver: glass, a glass bottle and a copper ingot.
- Sulfur Hood: copper ingots and bricks.

### Pure vs Minecraft
Pure and JUnit tested: `CalcinerLayout`. GameTests in `AlchemyGameTests`: forming in all four facings, a missing Receiver reported, breaking a shell unforms and drops Bricks, a calcine cycle on a formed Calciner, Salt only at the Ash Pan, the carrot does nothing, unformed does nothing. Manual: model, fire, smoke, fill levels, Visualize in the book, Jade.

## Risks / Trade-offs

- [Model pieces seam or look like separate blocks] → Pieces overhang into neighbours and share textures; play check before archive, art pass later in Blockbench.
- [Shell replacement loses a block if the server stops between steps] → Forming and unforming run in one call on the server thread, so a save never sees half a structure.
- [A player builds into another player's Calciner] → Forming makes the clicking player the owner and there is no build protection, like the Sink and the Athanor; acceptable on a cooperative server.
- [Fill level sync spams packets] → Send only when the drawn level changes by a step (sixteenths).
- [Jade API changes] → `compileOnly` on the version in `gradle.properties`, plugin kept tiny.
