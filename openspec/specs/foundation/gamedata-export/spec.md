# foundation/gamedata-export Specification

## Purpose

The game data export writes the effective balance data of the Servus mods (machine stats, recipes, deposits, techs, display names) to one versioned JSON file, so tools outside the game, such as the documentation site, see the numbers the game really uses.

## Requirements

### Requirement: Data run writes the game data file
The Alchemy data run SHALL write `docs/src/data/gamedata.json` at the repository root. The file SHALL contain a schema version number, the mod version, and sections for machines, recipes, crafting recipes, deposits, techs and items. The file SHALL be committed like other datagen output.

#### Scenario: Data run
- **WHEN** `gradlew :alchemy:runData` finishes
- **THEN** `docs/src/data/gamedata.json` exists and its `schema` field is `2`

### Requirement: Machine stats are effective values
Each machine entry SHALL hold the stats the machine uses at runtime: the values from its datapack file merged over its code defaults, so fields missing from the file appear with their default value. Each entry SHALL state its kind (burner, powered, crafter or generator) and the recipe types it runs.

#### Scenario: Partial machine file
- **WHEN** `burner_extractor.json` only sets `work_ticks` to 80
- **THEN** the burner extractor entry has `work_ticks` 80, `energy_per_tick` 0, `fuel_divisor` 1 and kind `burner`

#### Scenario: Default without a file field
- **WHEN** `crusher.json` sets no `work_ticks`
- **THEN** the crusher entry carries the crusher's code default for `work_ticks`

### Requirement: Recipes are exported with effective times
The export SHALL list every Servus assembling and crushing recipe, Servus smelting and blasting recipes, and the vanilla smelting and blasting recipes whose input appears in a Servus recipe, deposit yield or tech cost, repeated over the results of recipes already picked. Each recipe SHALL have its id, type, inputs with counts, outputs with counts, and its time with the codec default applied when the file omits it. Tag inputs SHALL be exported as tags.

#### Scenario: Recipe without a time
- **WHEN** the `crushing/raw_iron` recipe file has no `time` field
- **THEN** its exported time is the crushing default

#### Scenario: Vanilla smelting needed by a chain
- **WHEN** a deposit yields raw iron
- **THEN** the vanilla recipe smelting raw iron into an iron ingot is in the export

### Requirement: Output is stable
The export SHALL be deterministic: entries sorted by id, keys in a fixed order, pretty printed. It SHALL NOT contain timestamps or commit hashes, so running the data run twice on the same sources gives the same bytes.

#### Scenario: Repeat run
- **WHEN** the data run runs twice without source changes
- **THEN** `gamedata.json` is byte identical after both runs

### Requirement: CI rejects a stale export
The build workflow SHALL run the Alchemy data run and fail when `docs/src/data/gamedata.json` differs from the committed file.

#### Scenario: Hand edited machine file
- **WHEN** a commit changes `assembler.json` but not `gamedata.json`
- **THEN** the build workflow fails and names `gamedata.json` as out of date

### Requirement: Crafting recipes of all Servus mods are exported
The export SHALL list, in a crafting section separate from the production recipes, every recipe generated by Foundation, Alchemy and Shuttles that is not an assembling, crushing, smelting or blasting recipe. Each entry SHALL have its id, type, inputs summed per item or tag with counts, and outputs with counts. Production recipes and the vanilla cooking selection SHALL NOT change because of crafting entries.

#### Scenario: Power cable
- **WHEN** the Foundation power cable recipe uses six copper ingots, two redstone and one glass for eight cables
- **THEN** its crafting entry has inputs copper ingot 6, redstone 2, glass 1 and output power cable 8

#### Scenario: Chain data unchanged
- **WHEN** the shuttle recipe of Servus: Shuttles is exported
- **THEN** the production recipes section does not contain it and no vanilla recipe is added because of its inputs

### Requirement: Shaped recipes keep their grid
A crafting entry built on a grid SHALL also carry its pattern rows and the item or tag for each pattern symbol. This SHALL hold for vanilla shaped recipes and for Servus recipe types that use a shaped grid. Shapeless entries SHALL carry no pattern. Tag ingredients SHALL be exported as tags.

#### Scenario: Heavy rack
- **WHEN** the Shuttles heavy rack recipe uses its own recipe type with pattern `I I`, `PPP`, `I I`
- **THEN** its entry has those three rows, `I` as iron ingot, `P` as the planks tag, and inputs iron ingot 4 and planks tag 3

#### Scenario: Shapeless zone label
- **WHEN** the zone label recipe is shapeless with paper and the dyes tag
- **THEN** its entry has inputs paper 1 and dyes tag 1 and no pattern

### Requirement: Special recipes are marked
A recipe without fixed ingredients or result, such as the facade recipe, SHALL be exported as a crafting entry marked special, with its id and type and empty inputs and outputs.

#### Scenario: Facade
- **WHEN** the Logistics facade recipe is exported
- **THEN** its entry is marked special and has no inputs and no outputs

### Requirement: Item icons are rendered by a dev run
A dev client run with all Servus mods SHALL render every item listed in `gamedata.json` as a 64x64 PNG with a transparent background, the way the inventory draws it, and quit when done. Block items and items with composed models SHALL be drawn as their 3D GUI model with the GUI lighting; parts of a model that reach past the slot square MAY be cut. Icons of `servus_*` items SHALL be written to `docs/src/icons/<namespace>/<path>.png` and committed. Icons of other namespaces SHALL be written to the same tree but ignored by git. Without the run's system property the game SHALL NOT export icons.

#### Scenario: Export run
- **WHEN** `gradlew iconExport` finishes
- **THEN** `docs/src/icons/servus_shuttles/shuttle.png` exists, `docs/src/icons/minecraft/redstone.png` exists, and `git status` lists no vanilla icon

#### Scenario: Block items and composed models
- **WHEN** `gradlew iconExport` finishes
- **THEN** `docs/src/icons/servus_shuttles/heavy_rack.png` shows the Heavy Duty Rack block in the inventory's three quarter view and `docs/src/icons/servus_shuttles/shuttle.png` shows the composed shuttle model, each 64x64 with transparent corners and visible pixels

#### Scenario: Normal client
- **WHEN** the client is started with the normal run config
- **THEN** no icons are written and the title screen stays open

### Requirement: Items, deposits and techs are exported
The export SHALL list each deposit with its block and yield, each tech with its parents, cost, `ticks_per_pack` (default applied) and unlocks, and each item referenced anywhere in the file with its display name. Servus item names SHALL come from the English language files of all three Servus mods, including mods that are not on the Alchemy classpath; vanilla names SHALL come from the vanilla English language data.

#### Scenario: Tech with default lab time
- **WHEN** a tech file omits `ticks_per_pack`
- **THEN** its exported `ticks_per_pack` is the default

#### Scenario: Display names
- **WHEN** the export references `servus_alchemy:salt_crystal` and `minecraft:iron_ingot`
- **THEN** their names are "Salt Crystal" and "Iron Ingot"

#### Scenario: Shuttles item name
- **WHEN** the export references `servus_shuttles:shuttle`
- **THEN** its name is the one in the Shuttles English language file, not a title cased fallback
